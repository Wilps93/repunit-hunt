# Расширенный независимый пересчёт последовательностей (n ≥ 10⁴)

Приложение статьи опирается на сплошной пересчёт всех n < 10⁴ (`verify_sequences.sh`, каталог `verify/`). Выше 10⁴ полнота последовательностей берётся из OEIS. Скрипты ниже продолжают пересчёт диапазонами. Прерванный прогон при повторном запуске продолжается с места остановки.

## Файлы

| Файл | Что делает |
|---|---|
| `verify_range.sh BASE N_FROM N_TO [--double-check]` | Проверяет все простые n из [N_FROM, N_TO) для основания BASE с теми же настройками поиска, что `verify_sequences.sh`: конфиг по умолчанию, GPU TF, PRP auto (GMP до 2500 бит, дальше GWNUM), `--double-check ${DC:-0.05}`. Флаг `--double-check` задаёт долю 1.0. Диапазон режется на куски по `CHUNK` (по умолчанию 5000, границы кратны CHUNK). Готовые куски пропускаются, прерванный кусок продолжается по своему `worklog.jsonl`. |
| `verify_plan.py [--bench] [--dc R] [--from-markers]` | Для каждого из 20 оснований показывает сплошную границу, следующий диапазон (до 10⁵, затем до 3·10⁵), число простых n, ожидаемое число PRP-тестов и оценку времени при доле DC `R` и при DC = 1. `--bench` заново замеряет скорость на этой машине (около 1 минуты) и пишет `verify_ext/bench.json`. Без флага используется этот файл. `--from-markers` сравнивает модель с фактическим временем законченных кусков. |
| `compare_verify_ext.py [--base B] [-v] [--require-ext]` | Сверяет `verify/` (префикс n < 10⁴) и `verify_ext/` с b-файлами `data/`. Печатает сплошную границу X по каждому основанию, подтверждённые члены, а также лишние и пропущенные. Код возврата: 1 при любом расхождении. Если расширенных диапазонов ещё нет, сверяется только префикс и возвращается 0. С `--require-ext` в этом случае возвращается 2. |

### Что лежит в `verify_ext/`

- `chunks/b<b>/<a>_<c>.json` — маркер законченного куска. Он пишется, только если в журнале есть вердикт для **каждого** простого n куска (делитель, составное или PRP) и нет записей `failed`. Схема та же, что у `results.json` поисковика (`base`, `k_min`, `k_max`, `prp_exponents`), плюс статистика: число тестов, время, результаты double-check, ложные срабатывания GPU и времена отдельных PRP-тестов.
- `<b>_<from>_<to>.json` / `.txt` — итог по всему запрошенному диапазону, собирается, когда закрыты все его куски. `.txt` устроен как b-файл: шапка `#` с границами и строки `i n` по найденным PRP.
- `bench.json` — замер для `verify_plan.py`.

Рабочие каталоги с журналами (`worklog.jsonl`, `run.log`) лежат вне репозитория, в `$RH_WORK/b<b>/<a>_<c>/`, по умолчанию это `~/rh-verify-ext` внутри WSL. Удалять их после закрытия куска можно: авторитетен маркер.

## Что нужно

- **Поисковик, собранный в WSL** (README, раздел 3.1). На Windows проект не собирается: нативному слою нужен `gmp.h`, а под MSVC его нет, да и сам слой только под POSIX. Сборка в Ubuntu WSL2 занимает около 1,5 минут:
  ```bash
  wsl -d Ubuntu
  cd /mnt/c/Users/Dokuchaev_ts/work/repunit-hunt
  export CARGO_TARGET_DIR=~/rh-target
  cargo build --release
  ~/rh-target/release/repunit-hunt --devices   # должно быть: GMP=есть, GWNUM=есть
  ```
  `verify_range.sh` сам ищет бинарь в `$CARGO_TARGET_DIR/release`, затем в `~/rh-target/release`, затем в `<repo>/target/release`. Другой путь задаётся через `RH_BIN`.
- **GWNUM обязателен на практике.** Без него все тесты идут через GMP, а это примерно в 30 раз медленнее при 300 тыс. бит.
- **Запуск из Git Bash.** Скрипт сам перезапускается в WSL (дистрибутив задаётся `RH_WSL_DISTRO`, по умолчанию `Ubuntu`). В WSL передаются `DC`, `CHUNK`, `RH_WORK`, `RH_EXTRA_ARGS`, `RESTART` и `RH_BIN`, и пути в них должны быть путями **внутри WSL**. Не пишите в Git Bash `RH_WORK=~/...`: тильда раскроется в Windows-домашний каталог. Надёжнее запускать прямо из WSL.
- GPU необязателен: `RH_EXTRA_ARGS="--no-gpu"`. Без trial factoring до PRP доходит около 60 % простых n вместо 42 %, то есть тестов примерно в 1,4 раза больше.
- `verify_range.sh` и `verify_sequences.sh` берут общую блокировку (`/tmp/rh-verify.lock`). Одновременно может идти только один пересчёт.

Прочие переменные: `RESTART=1` начинает незаконченный кусок заново. Кусок, начатый с другими `DC`/`RH_EXTRA_ARGS`, скрипт продолжать откажется. Коды выхода: 0 — диапазон закрыт целиком; 1 — остались незакрытые куски (повторный запуск продолжит); 2 — ошибка окружения, аргументов или блокировки.

## Сколько это займёт

Оценка `verify_plan.py` по замеру 24.09.2026 (GTX 1650, 16 логических CPU, WSL2). Модель: PRP на GWNUM t ≈ 6,7·10⁻¹² · bits^2,31 с на поток, GMP t ≈ 3,0·10⁻¹¹ · bits^2,47 с. До PRP доживает 42 % простых n, эффективный параллелизм около 3,6. Проверка на реальном куске b = 10, n ∈ [60400, 60800): модель дала 47 с по стене, факт — 46 с.

| Этап | DC | Все 20 оснований | Основной набор (15) | Закроет членов OEIS |
|---|---|---|---|---|
| n < 10⁵ | 0,05 | ≈ 10,5 сут | ≈ 6,6 сут | 50 (42 в основном наборе) |
| n < 10⁵ | 0,01 | ≈ 5,5 сут | ≈ 3,5 сут | те же |
| n < 10⁵ | 1,0 (`--double-check`) | ≈ 131 сут | — | те же |
| n < 3·10⁵ | 0,05 | ≈ 390 сут | ≈ 244 сут | ещё 18 (13) |
| n < 3·10⁵ | 1,0 | ≈ 5200 сут | — | те же |

При 0,05 больше половины времени уходит не на основной тест, а на double-check. Сам GWNUM-проход до 10⁵ по всем основаниям занимает около 3 суток. Второй бэкенд — точный GMP, и при 300 тыс. бит он примерно в 34 раза медленнее GWNUM. Поэтому полный double-check (`--double-check`) на всём диапазоне до 10⁵ практически недоступен, хотя пересчёт n < 10⁴ для статьи шёл именно с `DC=1.0` (см. `validate.sh --full`).

Экстраполяция до миллиона бит (b = 26, n ≈ 3·10⁵) делается с замеров до 130 тыс. бит и может ошибаться в 1,5–2 раза. После первых законченных кусков уточняйте оценку: `python3 verify_plan.py --from-markers`.

### Какую долю double-check выбрать

Double-check ловит **ложное «составное»**, то есть потерянную находку, и только в выборке пересчитанных n. Положительные вердикты GWNUM и так всегда перепроверяются на GMP. Отсюда:

- Перепроверять участки вокруг *известных* членов нет смысла. Потерю известного члена `compare_verify_ext.py` покажет сам, как «ПРОПУЩЕН».
- Риск — потерянный *неизвестный* член. От него защищают только double-check по всему диапазону или повторный счёт. Реалистичный вариант: основной проход с `DC=0.05` (или `0.01`), затем выборочная перепроверка журналов `repunit-hunt --verify --verify-ratio R` в рабочих каталогах кусков. Её можно отложить и выполнять в фоне.
- В статье долю нужно указать честно (см. ниже).

## Рекомендуемый порядок

От дешёвых оснований к дорогим, как печатает `verify_plan.py` при DC 0,05: 2, 3, 5, 6, 7, 10, 11, 12, 13, 14, 18, 15, 19, 17, 20, затем расширенный набор 21, 22, 23, 24, 26. Если важнее закрыть b = 18 (сейчас подтверждён 1 член из 8, а ближайшие 25 667 и 28 807 лежат ниже 10⁵), начните с него: около 16 часов.

Из WSL (путь к репозиторию — ваш):

```bash
cd /mnt/c/Users/Dokuchaev_ts/work/repunit-hunt/paper
python3 verify_plan.py --bench          # один раз, ~1 мин
for b in 2 3 5 6 7 10 11 12 13 14 18 15 19 17 20; do
  bash verify_range.sh $b 10000 100000 || break
done
python3 compare_verify_ext.py
```

`|| break` останавливает цикл на незакрытом куске (код 1). Причина будет в `run.log` рабочего каталога. Повторный запуск того же цикла пропускает всё уже закрытое.

### Без присмотра

- **WSL/Linux:**
  ```bash
  cd /mnt/c/Users/Dokuchaev_ts/work/repunit-hunt/paper
  nohup bash -c 'for b in 2 3 5 6 7 10 11 12 13 14 18 15 19 17 20; do
                   bash verify_range.sh $b 10000 100000 || break; done' \
        > ~/verify_ext.log 2>&1 &
  tail -f ~/verify_ext.log
  ```
  WSL может погасить дистрибутив после закрытия последнего окна. Надёжнее оставить открытым окно `wsl` или использовать планировщик.
- **Windows, «Планировщик заданий»:** программа `wsl.exe`, аргументы
  `-d Ubuntu --exec bash -lc "cd /mnt/c/Users/Dokuchaev_ts/work/repunit-hunt/paper && for b in 2 3 5 6 7 10 11 12 13 14 18 15 19 17 20; do bash verify_range.sh $b 10000 100000 || break; done >> ~/verify_ext.log 2>&1"`.
  Включите «Выполнять вне зависимости от регистрации пользователя» и отключите остановку задания через 3 дня. Задание можно перезапускать хоть ежедневно: закрытые куски пропускаются, а занятая блокировка просто завершит второй экземпляр с кодом 2.

Прерывание безопасно в любой момент. В худшем случае заново посчитаются несколько PRP-тестов, не попавших в журнал до последнего сброса (раз в 60 с).

## Как внести результат в статью

Сейчас приложение A («Независимый пересчёт префиксов», `paper_ru.tex` / `paper_en.tex`) утверждает: проверены все n < 10⁴ по двадцати основаниям, каждый отрицательный вердикт пересчитан вторым бэкендом, подтверждено 153 члена (128 из 233 в основном наборе), и «выше 10⁴ полный пересчёт вычислительно недоступен».

После этапа n < 10⁵ `compare_verify_ext.py` напечатает по каждому основанию сплошную границу X, число членов ниже X и «новых» членов сверх префикса. Если все X = 100000 и расхождений нет, в тексте меняется:

1. «проверены все индексы $n<10^4$» → «$n<10^5$». Если какие-то основания не дошли до 10⁵, укажите границы по основаниям или минимальную.
2. «153 члена», «128 … из 233» → 153 + «новых» из итоговой строки (при полном этапе до 10⁵: 153 + 50 = 203 по всем двадцати, 128 + 42 = 170 из 233 в основном наборе). Пересчитайте по выводу скрипта, а не по этой оценке.
3. Фразу о double-check нужно **разделить**: для $n<10^4$ сплошной (доля 1), для $10^4\le n<10^5$ — выборочный, с долей R (0,05 или 0,01), плюс выборочная перепроверка журналов, если она была.
4. «Выше $10^4$ полный пересчёт вычислительно недоступен» → «выше $10^5$…». Можно добавить оценку: следующий шаг до 3·10⁵ стоит около года счёта на одной машине.
5. «Лишних нет, пропущенных нет» — оставить или заменить описанием расхождений.
6. Ссылку на скрипты в сноске и в разделе о доступности кода дополнить: `verify_range.sh`, `compare_verify_ext.py`, каталог `verify_ext/`.

Любое расхождение с OEIS — самостоятельный результат. Сначала перепроверьте этот кусок. Удалите его маркер `verify_ext/chunks/b<b>/<a>_<c>.json`: пока маркер есть, кусок пропускается. Затем запустите `RESTART=1 bash verify_range.sh <b> <a> <c> --double-check` и `repunit-hunt --base <b> --verify --verify-ratio 1.0` в рабочем каталоге куска. Сообщать в OEIS стоит только после этого.
