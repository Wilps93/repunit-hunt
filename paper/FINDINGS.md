## 2. Найденные дефекты

### 2.1. Фактическая ошибка в §3.4 (исправлено)

> «Основание 18 при концевой форме имеет Ĝ₁₈ = 0,6604 — **наибольшее значение
> среди всех пятнадцати**, то есть это "самое неудачливое" основание»

Неверно по **собственной таблице 5 статьи**: Ĝ₇ = 0,7104 и Ĝ₁₀ = 0,6612 больше.
Основание 18 — **третье**, а не первое. Вдобавок §1 той же статьи называет
«самым неудачливым» основание 7, что этой фразе прямо противоречит.

Упорядочение по убыванию Ĝ_b: 7 (0,7104), 10 (0,6612), **18 (0,6604)**, 3, 20, 2, …
Упорядочение по убыванию Ĝ_b^OLS: 7, 10, 3, 20, 14, 2, 15, 6, 5, **18 (0,4656)**, …

Содержательный вывод устоял и даже стал чётче: основание 18 переезжает
**с 3-го места на 10-е из 15** при смене формы оценки. Формулировка исправлена.

### 2.2. Правило отбора оснований в §2.2 не даёт заявленную границу (исправлено)

> «Верхняя граница b ≤ 20 выбрана как та, до которой последовательности OEIS
> содержат не менее восьми известных индексов у каждого основания.»

Проверено по OEIS: **A127996 (b = 21) содержит ровно восемь членов**
(3, 11, 17, 43, 271, 156217, 328129, 3078871), **A127997 (b = 22) — девять**.
Критерий впервые нарушается лишь при b = 23 (A204940, шесть членов). То есть
заявленное правило даёт границу b ≤ 22, а не b ≤ 20.

Это важно, потому что статья специально подчёркивает: «правило отбора
фиксировано заранее и не зависит от результатов». Неточная формулировка
подрывает именно этот тезис.

Исправление сделано в сильную сторону: граница честно названа условной круглой
величиной, и добавлена **прямая проверка её влияния** — расширение до всех
допустимых b ≤ 26 (B = 20, M = 253) даёт κ̂_B = 1,8285 вместо 1,8381, то есть
сдвиг 0,5 % (более чем на порядок меньше цены выбора схемы наблюдения), а критерий
однородности — Λ = 10,27, df = 19, p = 0,95. Ни один вывод не меняется.

### 2.4. Табл. 6: не оговорено правило выбытия основания (исправлено)

Подпись гласит «при n_min > 10⁴ одно основание выбывает (B = 14)». При
буквальном чтении (основание остаётся, если у него есть хотя бы одно событие,
N_b ≥ 1) **ничего не выбывает**: у b = 19 после усечения остаются 22051 и
209359, то есть N₁₉ = 1. Тогда последняя строка выглядит как
B = 15, M = 90, (M−1)/S = 2,0848, (M−B)/S = **1,7569**, p = 0,128.

Числа статьи (B = 14, M = 89, 2,0990, 1,7889) воспроизводятся **точно** при
правиле N_b ≥ 2. Правило верное, но его нужно назвать: без него диапазон
«схема B колеблется в пределах 1,79–1,87» превращается в 1,76–1,87.
Подпись переписана, обе версии последней строки приведены.

### 2.5. §7.2: сравниваются оценки по разным выборкам (исправлено)

> «λ̂ = (N−1)/(T−t₀) = 2,796 … Условная оценка того же основания даёт κ̃₂ = 1,922»

λ̂ = 2,796 посчитана по **50 дважды проверенным** показателям, а κ̃₂ = 1,922 —
по **всем 52** (это значение из табл. 5). На том же срезе из 50 показателей
κ̃₂ = **1,905**. Разница невелика, и вывод («различие невелико») сохраняется,
но сопоставлять величины с разных срезов нельзя. Текст исправлен: приведены обе
величины с явным указанием выборки.

### 2.6. §7.2: пуассоновское p-значение (исправлено)

Статья: p = 0,50. При μ₀ = 45,03 и 49 наблюдённых событиях:
удвоенный хвост даёт **0,59**, mid-p — **0,54**. Значение 0,50 не получается ни
при одной из общеупотребительных конвенций. Приведены обе с явным указанием
конвенции; вывод («рядовое наблюдение») не меняется.

### 2.7. §6: округление завышает требуемый рост фронтов втрое (исправлено)

Статья: «фронты должны вырасти примерно в **10²¹** раз». Точный счёт:
недостающие 657 событий при 9,6 события на удвоение всех пятнадцати фронтов —
это 68,2 удвоения, то есть 2^68,2 ≈ **3,3·10²⁰**. Округление вверх на порядок
в риторически нагруженном месте («вне досягаемости любых мыслимых вычислений»)
лучше не делать: 3·10²⁰ доказывает тезис ничуть не хуже.

### 2.8. §5.3: cv для мощности 80 % (исправлено)

Статья: cv ≈ 0,33 по сетке из шести точек с шагом 0,10–0,20 около перегиба.
На сетке из девяти точек (5000 реализаций на точку): cv = 0,30 → 0,693,
cv = 0,35 → 0,817, то есть 80 % достигается при cv ≈ **0,34**. Разница в
пределах точности, но сетку стоит сгустить, а точность — назвать. Таблица
мощности расширена.

### 2.9. Интервал ур. (12) не воспроизводился (исправлено)

Статья: [1,598; 2,099], p = 0,654. Процедура инверсии не была описана, поэтому
воспроизвести эти концы нельзя. Процедура записана явно (в §5.2 и в
`analysis.py`), и приведённые числа заменены на её вывод:
**[1,613; 2,130], p = 0,639**. Вывод не меняется. Заодно в английской
аннотации убрано слово «exact»: интервал схемы B получен инверсией симуляции
и точным не является — в отличие от интервала схемы A из гамма-пивота.

## 4. Побочный результат: баг в поисковике

Независимый пересчёт (п. 3.1) в первом прогоне разошёлся с OEIS на
**R_3181(23)**: GWNUM-бэкенд объявил число составным, тогда как это PRP
(подтверждено независимо арифметикой GMP: 2^(N−1) ≡ 3^(N−1) ≡ 1 mod N).

**Причина.** В `native/prp/prp_gwnum.c` ошибка округления FFT проверялась
раз в 128 итераций, а финальное значение `gw_get_maxerr()` после цикла
**записывалось в статистику, но не сравнивалось с порогом**. Для (b, k) =
(23, 3181) ошибка впервые превышает порог на итерации 14383 из 14384 — то есть
после последней периодической проверки на 14336-й. maxerr = 0,5000 (максимум
из возможных: остаток целиком мусор), но вердикт «составное» возвращался как
ни в чём не бывало. Это **потерянная находка** — ровно тот класс отказа,
который, как сам же README и пишет, не ловится ничем, кроме повторного счёта.

**Диагностика.** С margin = 1 длина FFT растёт с 768 до 1024, maxerr падает до
0,0015, вердикт верен. Через `gwsetup_general_mod` (без специальной формы)
maxerr = 0,0029, вердикт тоже верен. Частота: 1 случай на 96 пар (b, k)
в скане b ∈ {3, 7, 10, 13, 17, 19, 20, 21, 22, 23, 24, 26}, k ∈ {1009 … 10007}.

**Исправлено:**
1. `prp_gwnum.c` — финальная проверка порога с возвратом `RH_ERR_FFT_ERROR`,
   что запускает штатный перезапуск с увеличенным FFT.
2. `prp_dispatch.c` — если GWNUM не уложился за 4 попытки, кандидат
   досчитывается на GMP. Прежде возвращалась ошибка, а `pipeline.rs` на ошибке
   лишь пишет лог и **не создаёт записи в журнале** — показатель исчезал из
   результатов без следа. Второй путь потери находки.

**Проверка после исправления:** R_3181(23) — PRP за 0,057 с; R_49081(10)
(163 041 бит) по-прежнему находится за 4,2 с; `cargo test` 8/8;
`cargo clippy` — без замечаний; сплошной пересчёт всех двадцати оснований —
0 расхождений.

## 7. Рецензирование: математика, текст, литература

### 7.1. Предложение 3 было без доказательства, и его посылка неверна

Предложения 1 и 2 снабжены доказательствами, **предложение 3 — нет**: приведена
только формулировка. Хуже того, её ключевая посылка неточна:

> «Тогда δ_b ~ Exp(λ_b) в силу отсутствия последействия»

δ_b — расстояние от фронта до **последнего** события, то есть обратное время
возвращения. У процесса нет событий левее t₀, поэтому δ_b ≤ W_b по построению, и
ссылка на отсутствие последействия недостаточна: memorylessness даёт Exp только
для **прямого** времени. Точный закон — экспоненциальный, **усечённый** на W_b,
с атомом e^(−λW) в точке W_b (случай «находок нет вовсе»):

    E[δ_b] = (1 − e^(−λ_b W_b)) / λ_b,   не 1/λ_b
    E[κ Σ δ_b/ln b] = B − Σ e^(−λ_b W_b),   не B

**Написано полноценное доказательство**, добавлено замечание с оценкой
отбрасываемого остатка: Σe^(−N_b) < 3·10⁻³ против B = 15, то есть 0,02 %. Это
ровно та величина, которую показывает первая строка табл. 3 (+0,02 %), — вывод
не меняется, но утверждение теперь верно.

### 7.2. Та же неточность в §4.3

> «оценка κ̃_b по одному основанию несмещена при обеих схемах»

При схеме B оценка равна нулю при N_b ∈ {0,1}, а тождество для Beta применимо
лишь при n ≥ 2. Точный результат:

    E[λ̃_b] = λ_b − Pr(N_b = 1)/W_b = λ_b (1 − e^(−λ_b W_b))

— тот же экспоненциально малый дефицит (< 0,1 %). Формулировка исправлена.

### 8.4. Ложное расхождение и его причина

Первый полный прогон дал **«подтверждено 152, пропущен 1»** вместо 153/0/0 —
то есть якобы потерянный член последовательности. При повторной сверке тех же
файлов сразу получилось 153/0/0.

Невоспроизводимое расхождение опаснее постоянного, поэтому разбор был доведён
до конца. Причина оказалась не в поисковике и не в данных, а **в самой
процедуре проверки**:

- временные метки в `verify/` шли вразнобой: `b26.json` был **старше**, чем
  `b2.json`, хотя по порядку цикла основание 26 идёт последним;
- `ps` показал **два** одновременных `verify_sequences.sh`, причём один
  проработал уже шесть часов;
- это был мой самый ранний прогон верификации, **убитый по таймауту**: сам
  скрипт погиб, а порождённый им `repunit-hunt` осиротел и продолжал
  переписывать те же самые файлы;
- сверка прочитала каталог в промежуточном состоянии — отсюда мнимый пропуск.

Все двадцать журналов прогонов при этом показывали «Double-check: расхождений
0», то есть арифметика была верна всё время.

**Исправлено в инфраструктуре**, а не заклеено:

- `verify_sequences.sh` и `validate.sh` берут `flock`; второй одновременный
  запуск теперь отказывается стартовать с внятным сообщением;
- `validate.sh` ставит `trap` на INT/TERM и убивает потомков, чтобы прерванный
  прогон больше не оставлял живых процессов.

Мораль для отчёта: расхождение, которое не воспроизводится, нельзя списывать на
случайность — но и нельзя приписывать проверяемому объекту, не выяснив, кто
именно писал в файлы.

### 8.6. Расширение пересчёта нашло ещё два бага в поисковике

Подъём границы с n < 10⁴ до n < 2·10⁴ сразу дал расхождение: у b = 2 ожидалось
24 члена, найдено 23. **Пропал M₁₂₇₉ — известное простое Мерсенна.**

В журнале записи для k = 1279 не было вовсе; в логе — одна строка
`ERROR ... PRP k=1279: internal error`. Тот же k, посчитанный отдельно,
проходит без ошибок всеми тремя бэкендами: сбой проявлялся только под
многопоточной нагрузкой.

**Цепочка причин:**

1. `prp_dispatch.c` оценивал размер как `(k−1)·(floor(log2 b) + 1)`. Для b = 2
   это `(k−1)·2` вместо `(k−1)·1` — **завышение ровно вдвое**. Измеренный
   порог переключения на GWNUM (2500 бит) применялся к b = 2 как 1250 бит.
2. Число в 1279 бит уходило на GWNUM — в зону, где по собственным замерам
   проекта GWNUM медленнее GMP (при 1017 бит — в 10 раз), и где его настройка
   на слишком малом числе давала перемежающийся сбой.
3. `pipeline.rs` на ошибке лишь писал строку в лог и **не создавал записи в
   журнале**. Кандидат не «составной» и не «PRP» — он просто отсутствовал.

**Исправлено на всех трёх уровнях:**

- честный `log2` в оценке размера;
- при любой ошибке PRP кандидат досчитывается на GMP — она не зависит ни от
  FFT, ни от состояния GWNUM;
- если не вышло и это, пишется запись `"status":"failed"`, и показатель
  остаётся виден человеку и режиму `--verify`.

Проверка после исправления: b = 2 до n < 20000 даёт **24 из 24, ошибок 0**.

Этот баг было невозможно найти при границе 10⁴: там k = 1279 попадал в
диапазон, где сбой не возникал. **Расширение границы — не косметика.**
